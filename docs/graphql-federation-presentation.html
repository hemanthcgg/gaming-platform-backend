What is GraphQL?

The one-line version, before we split anything apart

One endpoint

Every request — read or write — goes to a single URL, unlike REST's many endpoints per resource.

Client asks for exact shape

The client specifies precisely which fields it wants; the server returns exactly that shape, nothing more.

Strongly typed schema

Every type and field is declared up front, so the contract between client and server is explicit and validated.

Schema building blocks

Our actual typeDef — the one we're about to split

This is the exact schema we're working from — one file, four types.

export const typeDefs = \`#graphql
  type Book {
    id: ID!
    title: String!
    authorId: ID!
    copiesCount: Int!
  }

  type Author {
    id: ID!
    name: String!
    description: String
    books: [Book!]!
  }

  type User {
    id: ID!
    name: String!
    email: String!
    password: String!
    borrowedBooks: [Book!]!
  }

  type Lend {
    id: ID!
    bookId: ID!
    userId: ID!
    lendDate: String!
    returnDate: String
  }
\`

Read operations — every field our current schema exposes, all under one Query type.

type Query {
  books: [Book!]!
  book(id: ID!): Book
  authors: [Author!]!
  author(id: ID!): Author
  users: [User!]!
  user(id: ID!): User
  transactions: [Lend!]!
  transaction(id: ID!): Lend
}

Our current typeDef has no Mutation type — it's Query-only. Here's a reasonable shape for the write operations this schema implies, so the recap is complete:

type Mutation {
  addBook(title: String!, authorId: ID!, copiesCount: Int!): Book!
  addAuthor(name: String!, description: String): Author!
  registerUser(name: String!, email: String!, password: String!): User!

  lendBook(bookId: ID!, userId: ID!): Lend!
  returnBook(lendId: ID!): Lend!
}

lendBook / returnBook matter most for the Router example later — they're the write path into the same Lend type we'll query.

The catch at scale

One server, one schema, one team's resolvers for everything — Book, Author, User, Lend all live in the same codebase, same file. That's fine for a small project. It breaks down as the schema and the team grow, which is exactly the problem federation solves.

Why federation

The monolith problem

What happens when one GraphQL schema keeps growing

One deploy unit

A typo in the Author resolver blocks shipping a fix to Lending. Everything ships together, or nothing does.

Team collisions

Multiple teams editing one schema file means merge conflicts and no clear ownership boundary.

Scaling is all-or-nothing

If only Lending is under heavy load, you still have to scale the entire monolithic server.

Schema sprawl

Every domain's types pile into one file — Book, Author, User, Lend, and whatever comes next.

Federation splits the schema by domain, into independently owned, independently deployed services — while clients still see one graph.

Concept 1 of 3

Subgraphs

An individual GraphQL service owning one domain of the schema

Why it's used

Each domain (Books, Authors, Users, Lending) becomes its own service with its own codebase, DB, deploy pipeline and team ownership.

Effective vs traditional approach

A traditional split means separate REST APIs the client stitches together itself, or a hand-rolled gateway. Subgraphs use directives (@key) so entities can be extended across services automatically, with one client-facing graph.

When it's ideal

  • Multiple teams own different domains
  • Domains scale and deploy at different rates
  • Schema has grown too large for one service

Disadvantages

  • More infrastructure — N services instead of 1
  • Cross-subgraph queries add network hops
  • Requires discipline around entity ownership
Concept 1 · code walkthrough

Converting the typeDef into subgraphs

Click each service to see exactly what its schema file looks like

Owns Author completely — unchanged fields, one new directive.

type Author @key(fields: "id") {
  id: ID!
  name: String!
  description: String
  /* "books" removed — books-subgraph owns it now */
}

type Query {
  authors: [Author!]!
  author(id: ID!): Author
}

Owns Book, and separately extends Author to add back the books field it just lost.

type Book @key(fields: "id") {
  id: ID!
  title: String!
  authorId: ID!
  copiesCount: Int!
}

extend type Author @key(fields: "id") {
  id: ID! @external
  books: [Book!]!        # resolved here: books where authorId = id
}

type Query {
  books: [Book!]!
  book(id: ID!): Book
}

Owns User — same pattern as authors-subgraph: fields unchanged, borrowedBooks removed (lending-subgraph adds it back).

type User @key(fields: "id") {
  id: ID!
  name: String!
  email: String!
  password: String!
  /* "borrowedBooks" removed — lending-subgraph owns it now */
}

type Query {
  users: [User!]!
  user(id: ID!): User
}

Owns Lend fully, and extends both User and Book to reconnect them.

type Lend {
  id: ID!
  bookId: ID!
  userId: ID!
  lendDate: String!
  returnDate: String
}
/* Lend has NO @key — nothing outside this subgraph
   ever needs to reference a specific Lend by id */

extend type User @key(fields: "id") {
  id: ID! @external
  borrowedBooks: [Book!]!   # resolved from Lend rows for this userId
}

extend type Book @key(fields: "id") {
  id: ID! @external
}

type Query {
  transactions: [Lend!]!
  transaction(id: ID!): Lend
}

Concept 2 of 3

Supergraph

The single composed schema describing the entire graph

Why it's used

Composition merges all subgraph schemas into one SDL, recording which subgraph resolves which field — the map the Router will use.

Effective vs traditional approach

Without it, you'd need to manually keep a hand-written unified schema in sync with N independent services. Composition generates and validates it automatically, every time a subgraph changes.

When it's ideal

  • Any time you have more than one subgraph
  • You want CI to catch breaking schema changes early

Disadvantages

  • Extra build step in your CI/CD pipeline
  • Composition errors (e.g. unshared duplicate fields) need understanding to debug
  • It's a static artifact — must be regenerated on every schema change

Composing with Rover

Two files and one command turn four schemas into a supergraph
federation_version: 2
subgraphs:
  authors:
    routing_url: http://localhost:4001/graphql
    schema:
      subgraph_url: http://localhost:4001/graphql
  books:
    routing_url: http://localhost:4002/graphql
    schema:
      subgraph_url: http://localhost:4002/graphql
  users:
    routing_url: http://localhost:4003/graphql
    schema:
      subgraph_url: http://localhost:4003/graphql
  lending:
    routing_url: http://localhost:4004/graphql
    schema:
      subgraph_url: http://localhost:4004/graphql

This reads the config, pulls each subgraph's schema, validates directives, and writes the merged SDL.

rover supergraph compose \
  --config ./supergraph-config.yaml \
  > supergraph.graphql

Author merged from two subgraphs — no trace of which one contributed which field.

Concept 2 · tooling

Why Rover, and what else exists

Rover is the CLI; here's what it actually does and its alternatives

What Rover does

Compose — merge N subgraph schemas into one supergraph SDL. Check — validate a schema change won't break composition or existing client queries, before merging. Publish — push a subgraph's schema to Apollo GraphOS for managed federation, where routers pull updates automatically.

ToolWhat it is
Apollo GraphOSNot a Rover alternative — its cloud companion. Rover is the CLI, GraphOS is managed federation (schema registry + auto-push to routers).
Mercurius FederationFederation support built into Fastify's GraphQL library — an alternative to the whole Apollo stack for Node-first teams.
WunderGraph CosmoOpen-source, self-hostable router + registry + composition — avoids Apollo vendor lock-in.
The Guild's HiveOpen-source schema registry, an alternative to GraphOS specifically.
GraphQL FusionAn upcoming vendor-neutral spec aiming to standardize federation itself.

One-line answer for "why Rover": it's the reference tooling for Apollo Federation — the spec our subgraphs use — but the open-source alternatives exist for teams who want managed federation without Apollo's paid tier.

Concept 3 of 3

Router

The runtime service that is the one GraphQL endpoint clients call

Why it's used

Loads the supergraph, plans each incoming query across subgraphs, executes the sub-requests, and merges results into one response.

Effective vs traditional approach

A hand-built API gateway needs custom stitching logic per query shape. The Router generates a query plan automatically from the supergraph — no per-query code to maintain.

When it's ideal

  • Clients should see one graph, not N services
  • Query shapes vary and change often

Disadvantages

  • Single point of failure if not made highly available
  • Adds latency — extra hop plus fan-out calls
  • Debugging a slow query means reading a query plan, not just one stack trace
Concept 3 · example

One request, step by step

author(id) { name books { title copiesCount } }
1. Client sends the query to the Router — the only endpoint it knows.
2. Router builds a query plan from the supergraph schema.
3. Router calls authors-subgraph for name and the entity key.
4. Router sends that key to books-subgraph as an entity representation.
5. books-subgraph resolves books via __resolveReference.
6. Router merges both results into one response shape.
7. Client receives a single JSON response.

Concept 3 · code walkthrough

Running the router, and what resolves the fan-out

The router binary's config, and the resolver that makes extension work
# router.yaml
supergraph:
  listen: 0.0.0.0:4000
include_subgraph_errors:
  all: true
./router --supergraph ./supergraph.graphql --config ./router.yaml

Apollo Router is a standalone Rust binary — not a Node process — even though every subgraph here is Node. It boots on :4000, the one URL our React frontend would ever call.

Lives in books-subgraph. Given just an id, it looks up that author's books locally.

const resolvers = {
  Author: {
    __resolveReference(reference) {
      // reference = { __typename: "Author", id: "a1" }
      // sent by the Router — books-subgraph only needs the id
      return { id: reference.id };
    },
    books(author) {
      return db.books.filter(b => b.authorId === author.id);
    }
  }
};

The chain, in one line

Subgraphs (own schemas) → composition → Supergraph (one schema, static) → Router (runtime, uses the supergraph to serve live queries).

Wrap-up

Key takeaways

Subgraphs

Split by domain. Entities need @key; value types don't. Extension is always flat, never chained.

Supergraph

A build artifact, not a service. Regenerate it whenever a subgraph schema changes. Rover composes it; GraphOS/Cosmo/Hive manage it at scale.

Router

The single endpoint clients see. It plans, fans out, and merges — automatically, per query.
